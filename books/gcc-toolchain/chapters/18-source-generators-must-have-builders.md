# Source generators must have builders

A generated C file is an input to compilation, but it was also someone’s output.
How far back must we follow that producer before the bootstrap story stops
borrowing an unexplained parser?

Begin with GCC’s small gencheck lesson, then trace the actual oyacc → Heirloom
lex → flex recipe. Generated text, executable producers and comparison oracles
will keep separate identities.

This is a paper lesson at the [pinned edition](../../EDITION.md). Its worked
states use inspected repository contracts and explicitly supplied inputs.
Existing results are attributed to their recorded source accounts; no new
compiler, generator, runtime, toolchain or produced program was executed for
this manuscript.

## Bring the needed contract

G17 supplies captured sources and Makefile-selected work. A **generator** is an
executable that reads descriptions and writes source/data for another build
step. It runs on the build machine even when its output will describe a later
target. Source acquisition, shell, make, sed and patch remain identified host
services.

## Give one small generator a concrete output

The recorded gencheck check uses the original Makefile’s configured
language-tree list to make gencheck.h, bconfig.h, tm.h and build/gencheck.o with
actual build flags. The Forth linker creates build/gencheck-direct, which emits
tree-check.h on stdout. The expected-output comparison lives in Python memory
and supplies no production generated bytes.

The complete Makefile link also requires BUILD_LIBIBERTY. This earlier narrowed
link against the bounded source-built runtime establishes its direct symbol
needs, not the full archive dependency. That distinction lets the first story
end with a real named generator before the complete census opens every library
rule.

We have not run gencheck again. This is the pinned repository’s recorded recipe
and scope, not a fresh execution or verified first-reader command card. It earns
the producer question: who built the generator, what descriptions/configuration
did it read and which exact bytes did its consumer use?

## Build the first parser generator from verified sources

lexers.py verifies and prepares oyacc 6.6, Heirloom devtools 070527 and flex
2.5.11 from archived inputs and recorded recipe-reference bytes. It invokes
oyacc’s production-only build through the Forth compiler, then uses the
resulting oyacc to generate Heirloom parser C from parser.y.

Forth compiles Heirloom’s ordinary lex units and links them with source-built
startup/runtime. Its five-member libl.a contains allprint, libmain, reject,
yyless and yywrap. These are target objects built from C, not a host lex library
borrowed because the archive has a familiar filename.

Parser/scanner C shipped in a release is not quietly accepted as the initial
generated input in this recipe. Archive hashes, preparation records, notices and
licenses retain the lineage of actual descriptions and adaptations. Flex 2.6.4
is not a hidden required ancestor.

## Make a temporary scanner, then replace it

oyacc generates flex’s parse.c and parse.h. Heirloom lex cannot directly provide
every behavior needed by the final flex scanner, so the recorded restricted
scan.lex.l creates a temporary scanner. The source preserves that input and
writes scan-ascii.l, changing one U+0160 letter in its copyright comment because
C-locale wide I/O rejects the UTF-8 byte sequence.

The generated lex.yy.c is retained as heirloom-scan.c, and its symbol spelling
is adapted into scan-tmp.c. Forth compiles the flex units with that temporary
scanner to build flex-tmp. That executable then processes the patched original
scan.l, producing scan.c. Forth recompiles that scanner and relinks the final
flex.

The temporary scanner is not claimed equivalent to the full scanner. Its purpose
is to build the producer that replaces it. Preserve both hashes and the exact
adaptation reason; neither a comment-only edit nor an independently checked
skeleton transform makes source preparation disappear from the trust graph.

## Let header probes produce their own answers

The flex recipe compiles actual header-test sources with the production Forth
driver before adding HAVE_* definitions to config.h. It records command, return
code and diagnostics. It does not prefill the answers merely because the build
author expects a header to work.

The entire recipe uses one compiler identity, checked before and after the
generator chain. Produced executables, archives and generated C inputs receive
retained hashes. Original and adapted scanner sources, patch commands/output and
source-preparation record remain separately identified.

That record distinguishes description files, generated files and executable
builders. An output hash without its producer/source/configuration tuple is a
checksum, not a reconstruction of how that file entered the route.

## Revisit the complete GCC generators

gengenrtl emits genrtl.c and genrtl.h from original rtl.def and audited
configured branches. Its first independent inventory mistakenly counted both
conditional alternatives; the repository records an oracle inventory correction
rather than a compiler failure. Complete byte comparison with a separately
host-built generator is stronger than marker coverage, while still supplying no
production text.

genmodes uses five selected libiberty members and the documented C_alloca frame

generators and consumers. A selected-library proof does not become full

## Draw a generator as an executable node

A generated C file has a producer just as an object file does. Supply a grammar,
an identified yacc executable and its skeleton inputs. The parser C is their
output. Compiling that C with Forth establishes the object producer, but it does
not identify the executable that originally generated the C.

The direct route therefore builds source generators too. The recorded chain
gives oyacc a real source-built executable, uses Heirloom lex to produce a
temporary scanner, then uses a temporary flex to generate flex's replacement
scanner. Each replacement is a specific handoff. “Self generated” describes one
arrow; it does not erase the earlier arrows that made the generator executable
available.

An oracle can generate a comparison file using an existing host tool. That
comparison output belongs to the evidence branch unless the production recipe
actually consumes it. Draw both branches and label which file feeds the next
compiler invocation. Without that label, a byte match can conceal a
host-produced production input.

## Retain the prepared source as a real input

The temporary scanner needs the documented adaptation to comment handling. Treat
it as an exact source preparation step, with the checked bytes and rationale
retained. The goal is to make the source compilable under the admitted compiler,
not to pretend the original file was accepted unchanged.

Likewise, the Heirloom library selection is a finite set of needed objects, not
an assertion that the route built every utility in that source distribution.
Scope the achievement to the selected generator and its dependencies. Broader
upstream compatibility would need its own build and test evidence.

The provenance records identify source origins and license-bearing adaptation.
Licensing text is part of the retained source account; it is not evidence that
the generated program behaves correctly. Conversely, successful behavior would
not identify which adaptation or source version produced it. Preserve both kinds
of records without asking one to do the other's job.

## Ask what a small generator comparison proves

The GCC generator probes retain specific output sizes and byte-comparison
results. A matching output on the named input establishes agreement for that
input under the named comparison. It does not establish that all grammar forms,
all target descriptions or every future invocation will agree.

A useful later record includes executable hashes, input hashes, invocation
arguments, output bytes and comparison status. A filename such as `genmodes` is
insufficient when several generations of the same tool exist. The source-built
output and oracle output should be separately identifiable even if their hashes
agree.

The selected generator chain is needed before the compiler's generated
translation units can be treated as source-built inputs. G19 can then ask about
cc1's behavior without hiding this preparation stage. The chapter relies on the
pinned records for existing generator results. No new parser, scanner or GCC
generator was compiled or executed for the manuscript.

## Retain a replacement chain without skipping its temporary node

For the scanner chain, keep four differently named products: the restricted
scanner description, Heirloom's generated scanner, the adapted temporary C
scanner, and flex's regenerated final scanner. They are not interchangeable
copies of one input. Each belongs to a specific production step.

The one U+0160 transliteration changes an attribution comment so the selected
C-locale wide I/O can process the temporary description. The recipe verifies the
occurrence count and resulting ASCII input, then records original/adapted hashes
and the reason. That is a bounded preparation operation rather than a general
character-normalization policy.

The temporary generated C changes the scanner symbol spelling before
compilation. flex-tmp then consumes the patched original scan.l and replaces
that scanner. Retaining the intermediate before replacement makes the chain
inspectable. Without it, a final scanner hash would identify the endpoint while
concealing how its producer became executable.

| Produced artifact | Immediate executable producer | Later consumer |
|---|---|---|
| Heirloom parser C | Forth-built oyacc | Forth C compiler |
| Temporary scanner C | Forth-built Heirloom lex | Prepared flex-tmp build |
| Final scanner C | Forth-built flex-tmp | Forth C compiler |
| Final flex executable | Forth compiler/linker plus runtime | Later scanner generation |
| GCC generated header | Named Forth-built GCC generator | GCC source compilation |

The five-member Heirloom libl archive closes its selected lex/flex support
needs. The five selected libiberty members in the genmodes story close a
different narrow generator link. Their equal member counts do not make them the
same library or the same proof. Name the member set and consumer whenever
reporting either closure.

The header probes in lexers.py use the production compiler and retain individual
statuses before generating config.h. Those are stronger inputs than silently
asserting that every familiar header exists. They still do not certify complete
scanner semantics or wide/EUC variants outside the recorded scope.

For a later run, retain every executable identity, generated source, adaptation
record, recipe and output comparison. Oracle products belong beside the
production graph with their own tools. This manuscript attributes existing
generator sizes and comparisons to the pin; it has not regenerated scanners or
repeated those measurements.

## Follow the retained genmodes failure through its repair

The machine-mode generator story starts with a finite source-built library
closure. Five libiberty members are compiled and archived under the original
Make rules, including the target-guarded C_alloca adapter. The original GCC
Makefile then links genmodes with that actual archive. This is a real
BUILD_LIBIBERTY input for the selected generator, while full-library failures
remain separately recorded.

Before executing, the check preserves preprocessing and verifies the computed
target-definition include. GCC's i386 mode definitions add target-specific modes
and formats. A generator that runs using an incomplete include set can produce
plausible output while missing those facts. The incomplete historical object is
retained under a quarantined name and does not enter the accepted route.

The independent host oracle builds unchanged generator/library source with the
same configured branch facts and native original C_alloca behavior. Its complete
outputs are compared with production, while all oracle artifacts stay in a
separate tree. This comparison addresses output bytes; marker coverage alone
would be weaker.

The first complete-target comparison exposed physical backslash-newline handling
inside string literals. Extra output newlines appeared where line splicing
should have removed the physical pair before the literal was interpreted. This
is a source-preprocessing boundary whose effects became visible in generated
text. A successful generator exit did not establish correct output.

After the recorded repair, the three complete outputs match the independent
oracle. The account gives 3,522 bytes for insn-modes.h, 4,589 for
min-insn-modes.c and 16,715 for insn-modes.c. Those numbers identify the
documented case and outputs. They are not newly measured sizes or a guarantee
for arbitrary target descriptions.

The later full-current-core replay compares the object and output bytes against
the previous narrower compiler composition. The final proof also reruns the
original configure scripts on the full current source and preserves probe
traces. Read these as additional named events with their own configurations
rather than as consequences of the earlier narrow generator link.

C_alloca's adapter is another concrete preparation. Its original local-address
depth estimate failed when a nested argument changed temporary stack depth. The
private __seed_parent_frame metric uses the selected stable RBP chain. An
observer can track reclamation independently of production, but that observer is
not linked into the generator. This gives both a runtime interface and a
test-support role in one small account.

The chapter's generator chain therefore includes successful products, rejected
historical products, source repairs, narrow library scope and separate oracles.
Retaining them makes the achievement stronger and more precise. We have not
rerun these checks, reapplied the repair or generated new comparison outputs for
the book.

## Stop, then change the boundary

Save the worked state you can now explain, including its owner and the phase at
which it changes. Reconstruct that state before moving to a changed case. If a
result differs, locate the first changed premise rather than replacing the final
number until it agrees.
